# RFC: Keeli v5.1 "Grounded Logic" Engine

## Background
In Keeli v4.0, task status was managed primarily in metadata. If a file was manually moved between directories (e.g., from `backlog/` to `active/`), the internal `**Status:**` metadata would become stale, creating a split-brain problem between the physical filesystem and the indexing layer.

## v5.1 Architecture: Grounding
v5.1 establishes the **Physical Directory Structure** as the canonical status signal.

1. **Folder Authority**: The directory containing a task file (`docs/tasks/{status}`) determines its state in the `task_index`.
2. **Auto-Reconciliation**: The `sync()` engine detects mismatches between folder location and file metadata. If a mismatch is found, the file metadata is overwritten to match the folder.
3. **Optimistic Locking**: Every task modification via MCP or CLI requires a `VERSION_HASH` (SHA256 of full file content). This prevents "Stale Overwrite" bugs when multiple agents or humans are editing the same workspace.

## Key Components

### 1. Persistent Audit Log
A local SQLite `audit` table records every transition, identifying whether the actor was a `system` (sync), `developer` (cli), or `agent` (mcp).

### 2. Token-Budgeted Digest
The `digest` tool implements SectionPriority truncation (cl100k_base):
- Priority 1: Current Session Focus & Branch
- Priority 2: Active Task Metadata
- Priority 3: Recent Audit Integrity
- Priority 4: Project Overview (README)

### 3. Context Waterfall
Context variables (`context_resolve`) use a hierarchical lookup:
`Session > Git Branch > Global`

## Convergence Model
When `keeli sync` (or any read operation) is called:
1. Walk `docs/tasks/{status}`.
2. If file content hash has changed or folder has moved:
   - Re-parse file.
   - If folder != `**Status:**`, update file content.
   - Update SQLite `task_index`.
   - Update `audit` log.
